### GigaSpeech2 th หักล้างคำอธิบายเรื่อง "แพ้เพราะวิธีเขียน"

ชุดที่สอง `speechcolab/gigaspeech2` config `th` split `test` (50 ตัวอย่าง ดึงด้วย
`../fetch_gigaspeech2.py`) เป็นคลิปพูดคุยทั่วไป ยาว p50 4.70s และ **ไม่มีตัวเลข
หรือคำอังกฤษเลยสักประโยค** ไฟล์ `gs2_*.json`

| | Pathumma RNNT | Typhoon ASR |
|---|---|---|
| CER realtime | **12.40%** | 17.07% |
| CER final | **12.96%** | 17.33% |
| ถูกเป๊ะ | 5/50 | 2/50 |

Pathumma ยังชนะ 4.4 จุดทั้งที่ไม่มีตัวเลข/อังกฤษให้ต่างกันเรื่องรูปแบบ และชนะทุกช่วง
ความยาว (0-3s: 26.97 vs 33.33, 3-5s: 11.53 vs 16.71, 5-20s: 10.41 vs 14.15)
มีทั้งกรณีที่เป็นการฟังผิดล้วน ๆ:

```
ref     : ฝั่งด้านนี้ก็จะเป็นแบบโซนต้นไม้ต้นใหญ่นะครับสามารถที่จะมาดูได้เลยนะ
Pathumma: ฝั่งด้านนี้ก็จะเป็นแบบโซนต้นไม้ต้นใหญ่นะครับสามารถที่จะมาดูได้เลยนะ  (err 0)
Typhoon : ก่อนหน้านี้ก็จะเป็นแบบส่วนต้นไม้ต้นใหญ่นะครับสามารถที่จะมาดูได้เลยนะ  (err 10)
```

**สรุปที่แก้แล้ว:** เรื่องรูปแบบการเขียนอธิบายได้แค่ส่วนหนึ่งของช่องว่างบน Ratchada
ไม่ใช่ทั้งหมด Pathumma ถอดเสียงได้ดีกว่าจริงด้วย ที่ Ratchada กลุ่มไทยล้วนออกมาเสมอกัน
(18.20 vs 18.64) น่าจะเพราะเป็นชิ้นสั้น p50 1.58s ที่ตัดกลางประโยค ซึ่งทั้งคู่ทำได้แย่
พอ ๆ กันจนกลบส่วนต่าง — ไม่ใช่หลักฐานว่าความสามารถเท่ากัน

ข้อสังเกตเรื่องรูปแบบยังจริงอยู่ แต่ทิศทางสลับตามชุดข้อมูล และ Pathumma บังเอิญตรงกับ
เฉลยทั้งสองแบบ: Ratchada เฉลยเขียน `34.5` / `gross profit margin` (Pathumma ตรง),
GigaSpeech2 เฉลยเขียน `เอ็มอาร์ที` ส่วน Typhoon เขียน `MRT` (Pathumma ตรงอีก)

### ส่วนต่างบน Ratchada มาจากวิธีเขียนเป็นหลัก

สาเหตุคือ Typhoon ถอดทุกอย่างเป็นอักษรไทย ส่วน Pathumma เขียนเลขอารบิกกับอักษรละติน
ซึ่งตรงกับ `label` ของ dataset:


### Whisper ไม่ได้แค่แม่นน้อยลง — pipeline มันพัง

ตัวเลข 52.82% อ่านว่า "ความแม่นของ Whisper large-v3" **ไม่ได้** มันคือ RealtimeSTT
ทิ้งเสียงทิ้งกลางคัน หลักฐาน:

- latency ติดลบ 16/30 คลิป (ประโยคสุดท้ายมาถึง**ก่อน**เสียงจะหมด) ต่ำสุด -29.8s
- ได้ 1.6 ประโยค/คลิป เทียบ 2.7 ของ RNNT
- อัตราส่วนความยาวข้อความที่ได้ต่อเฉลย p50 0.81 **ต่ำสุด 0.11** สูงสุด 1.88
  (RNNT p50 0.97 ช่วง 0.75–1.03)

สาเหตุอยู่ที่ `audio_recorder.py:73` `ALLOWED_LATENCY_LIMIT = 10` และ `:1258`

```python
while self.audio_queue.qsize() > self.allowed_latency_limit:
    data = self.audio_queue.get()      # ทิ้งเสียงเก่าทิ้งเงียบ ๆ
```

ถอด buffer 29 วินาทีด้วย beam_size 3 ใช้เวลาถึง **18.68s** (ค่าสูงสุดที่วัดได้)
ซึ่งช้ากว่าเวลาจริงมาก เสียงที่ไหลเข้ามาระหว่างนั้นจึงล้นคิวแล้วถูกทิ้ง
RNNT ถอดเร็วกว่าเวลาจริงมาก คิวไม่เคยตัน ปัญหานี้จึงไม่เกิด

**ข้อจำกัดนี้เป็นของ pipeline ไม่ใช่ของโมเดล** ถ้าจะใช้ Whisper กับเสียงยาว ต้องขยาย
`allowed_latency_limit` หรือเปลี่ยนสายเรียลไทม์เป็นโมเดลเล็ก (ซึ่ง config จริงของ
โปรเจกต์ใช้ distill-small อยู่แล้ว จึงน่าจะดร็อปน้อยกว่านี้ — ยังไม่ได้วัด)

### ผลพลิก: Typhoon ชนะบน long-form

Typhoon แพ้ Pathumma RNNT ทั้ง Ratchada (31.64 vs 26.34) และ GigaSpeech2

## noise floor — อ่านก่อนสรุปว่าอะไรดีกว่าอะไร

`out_fp16.json` กับ `rt_fp16.json` คือ **config เดียวกันเป๊ะ ชุดเดียวกันเป๊ะ** รันคนละรอบ
ได้ 30.41% กับ 32.07% ต่างกัน **1.66 จุด**

สาเหตุคือ harness สตรีมตามเวลาจริง จุดที่ VAD ตัดประโยคจึงขึ้นกับ wall clock และภาระ GPU
ขณะนั้น เสียงที่ป้อนเข้าโมเดลแต่ละรอบไม่เท่ากันเป๊ะ

**ผลที่ตามมา:** ส่วนต่าง fp16 vs int8 ที่ 2.8 จุด สูงกว่า noise แค่นิดเดียว ยังสรุปไม่ได้แน่น
ถ้าจะเทียบ compute_type หรือโมเดลที่ต่างกันไม่มาก ต้องรันซ้ำหลายรอบแล้วดูค่าเฉลี่ย
ส่วนต่าง realtime vs final ที่ 6.4 จุด ถือว่าเกิน noise ชัดเจน เชื่อได้
